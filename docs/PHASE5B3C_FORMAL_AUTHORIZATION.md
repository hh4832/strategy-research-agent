## 4. What this PR's code adds (so the signed PR stays green and fail-closed)

`b3c.formal_authorization_state()` is the only place where a new authorization is accepted. It classifies the books into one of four states:

| State | Condition |
|---|---|
| `NOT_GRANTED` | The book holds only the known spent authorizations |
| `GRANTED_UNUSED` | Exactly one APPROVE for this ID, all of the following hold, and the uses count is 0 |
| `GRANTED_USED` | Same conditions as above, but uses have been recorded |
| `UNEXPECTED` | Anything else; it always fails |

For `GRANTED_*`, the APPROVE must:
- be signed by an allow-listed lead;
- have an `approval_ref` that is a github.com URL;
- be byte-equal to the committed proposal, and that proposal must pass every proposal-time check;
- have the committed run config equal to `derive_run_config(ID)`.

These checks are now state-aware through that function, instead of assuming "no authorization exists":
- B3-A G3;
- B3-B `production_state`. It is still refused without the live verifier: the real path is never constructed there.
- the Phase 4-A book test;
- the B3-C preflight and its tests;
- CI.

Simulated post-signing state (isolated worktree, never pushed):
- all suites pass;
- `append_only_guard` PASS;
- preflight = `AUTHORIZED_AWAITING_GITHUB_APPROVALS`, all B3C gates `NOT_EXECUTED`.

Tamper tests confirm that each of these yields `UNEXPECTED`:
- an edited config;
- an edited proposal;
- a non-GitHub ref;
- a second line;
- an unknown authorization;
- a missing config.
